# Лабораторна робота № 2

**Тема:** розробка консольних утиліт для задач кібербезпеки.  
**Варіант:** 8 — фільтр та аналізатор журналів DNS-запитів.

## Запуск

Виконуйте команди з кореня репозиторію. Залежність Ruff зазначена у спільному
`requirements.txt`.

```powershell
python -m pip install -r requirements.txt
python -m labs.lab02.main demo
python -m labs.lab02.main analyze --dns-log labs/lab02/data/data_v08/dns_queries.csv --blacklist labs/lab02/data/data_v08/blacklist.txt --out-csv labs/lab02/data/dns_alerts.csv --min-domain-len 50 --log-file labs/lab02/data/dns_audit.log
```

`demo` показує сценарії ООП Завдання 1. `analyze` читає DNS-журнал, виводить
кількість запитів за типами, показує підозрілі записи, зберігає CSV-звіт і лог.

## Дані варіанта 8

Вхідні файли розпаковано з наданого `lab2_data.zip` зі збереженням каталогу
варіанта:

```text
labs/lab02/data/data_v08/
├── blacklist.txt
└── dns_queries.csv
```

Звіт і журнал роботи зберігаються окремо у `labs/lab02/data/dns_alerts.csv` та
`labs/lab02/data/dns_audit.log`.

CSV має заголовки `Timestamp,ClientIP,Domain,QueryType`, дата й час подані в
ISO 8601. Парсер приймає ці заголовки без урахування регістру, а також snake_case
варіант. Чорний список містить по одному домену на рядок; порожні рядки й
коментарі з `#` ігноруються. Файли `dns_queries.csv` та `blacklist.txt` у батьківській
папці `data/` є копіями тих самих вхідних даних для зручності.

Аргументи `analyze`:

| Аргумент | Призначення |
| --- | --- |
| `--dns-log` | Обов'язковий шлях до CSV журналу. |
| `--blacklist` | Обов'язковий шлях до текстового чорного списку. |
| `--out-csv` | Обов'язковий шлях до звіту зі спрацюваннями. |
| `--min-domain-len` | Поріг довжини домену для довгого TXT-запиту; типово `50`. |
| `--log-file` | Необов'язковий шлях до логу; новий запуск перезаписує його. |

Утиліта рахує запити типів A, AAAA, MX, TXT та інших. Вона позначає точні
збіги з чорним списком, довгі DNS-мітки, окремі підозрілі TLD, довгі TXT-запити
та високоентропійні піддомени. Це евристики для перевірки, а не підтвердження
атаки. Некоректні CLI-аргументи обробляє `argparse`; відсутній файл, неправильні
заголовки чи некоректний запис дають повідомлення й код завершення `2`.

## Завдання 1: модель облікового запису

`Admin` успадковує `User` за принципом Is-A. `UserAccount` містить `User`,
`Session` і `AuditLog` за принципом Has-A. Незмінний `AuditRecord` описаний через
`@dataclass` із явними полями часу, користувача й дії. Пароль зберігається лише
як PBKDF2-HMAC-SHA256 із випадковою сіллю; хеші порівнюються
`hmac.compare_digest`.

## Контрольні питання

1. Інкапсуляція об'єднує стан і методи. `_name` — домовленість про внутрішній
   атрибут; `__name` активує name mangling для уникнення випадкових конфліктів.
2. `@property` зберігає інтерфейс атрибута й дозволяє перевірку при читанні та
   записі.
3. `Admin` є `User` (Is-A); `UserAccount` має користувача, сеанс і аудит (Has-A).
4. `__getitem__` і `__setitem__` дозволяють `account["user"]` із перевіркою
   ключів і типів.
5. `@dataclass` зазвичай генерує `__init__`, `__repr__`, `__eq__`; він зручний
   для структур даних із визначеними полями.
6. `pathlib.Path` дає переносимі об'єктні операції над шляхами та файлами.
7. `Counter` агрегує частоти, а `defaultdict` автоматично створює початкові
   значення груп.
8. `argparse` перевіряє аргументи й типи до виконання логіки програми.
9. `logging` підтримує рівні, форматування та запис у файл; рівні від DEBUG до
   CRITICAL показують деталізацію й серйозність.
10. Ruff перевіряє стиль і частину типових помилок. Для всього проєкту виконайте
    `ruff check .` і `ruff format --check .`.
