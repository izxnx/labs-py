## 1. Варіант і правило відбору

Напрям відбору — **зміна меж впливу**. Правило:

```text
score >= 9.0  і  cvssData.scope == "CHANGED"
```

Метрика `scope` (S) у CVSS v3.1 показує, чи виходить вплив успішної атаки
за межі повноважень (security scope) уразливого компонента. `UNCHANGED` —
наслідки обмежені самим компонентом; `CHANGED` — атака зачіпає ресурси
іншого компонента з іншими повноваженнями (наприклад, втеча з
гіпервізора, браузерної пісочниці чи контейнера). Поєднання `CHANGED` із
дуже високою базовою оцінкою (≥ 9.0) — навчальний критерій для ручного
огляду, а не пріоритет усунення в реальній системі.

Оцінка та ознака беруться з однієї вибраної оцінки CVSS v3.1: першої з
`type = "Primary"`, інакше — першої у списку.


Результат (код завершення 0):

```json
{
  "cve_id": "CVE-2099-10001",
  "variant": 8,
  "description": "Synthetic vulnerability for offline API testing.",
  "vuln_status": "Analyzed",
  "cvss_version": "3.1",
  "score": 9.8,
  "score_source": "nvd@nist.gov",
  "vector": "CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H",
```

Оцінка 9.8 перевищує поріг, але `scope = UNCHANGED`, тому рішення
`other`, як і очікується методичкою для варіантів 8–15.

## 3. Тести та Ruff

```text
> python -m pytest labs/lab04/tests -q
162 passed

> ruff check labs/lab04
All checks passed!

> ruff format --check labs/lab04
10 files already formatted
```

Що перевіряють тести:

- **межа порога** — оцінки 8.9 → `other`, 9.0 → `review`, 9.1 → `review`
  за `scope = CHANGED`; 10.0 з `UNCHANGED` → `other`;
- стани `not_found`, `rejected` (навіть за високої оцінки),
  `insufficient_data` (немає статусу, оцінки v3.1 або поля `scope`);
- помилки даних: `scope = null`/`"changed"`/число, `baseScore` як `true`,
  рядок `"9.8"`, `NaN`, `inf`, значення поза 0–10, неправильні типи
  `metrics`, `cvssMetricV31`, `cvssData`, `version != "3.1"`;
- пріоритет `Primary` над попередньою `Secondary` і вибір першої оцінки
  за відсутності `Primary`; оцінка й ознака з однієї оцінки;
- клієнт: точні URL, `params={"cveId": ...}`, `timeout=(3.05, 10)`,
  `allow_redirects=False`, заголовки з вигаданим ключем і без нього;
  таймаути, помилки з'єднання, HTTP 404/429/500/503, статуси 204/301,
  некоректний JSON — через підміну `requests.get`;
- CLI: локальний режим не викликає мережу, відсутній файл, некоректний
  JSON, не-UTF-8 файл, неправильний `--cve` (код 2), неправильний
  номер варіанта (код 2), ключ і текст винятків не потрапляють у вивід.

**Тест на межі порога.** Рівність `score == 9.0` перевіряється окремим
параметризованим випадком. Експеримент: після заміни `>=` на `>` в
`analysis.build_report` впав рівно один тест
`test_decision_by_score_and_scope[9.0-CHANGED-review]`
(`1 failed, 161 passed`). Після відновлення `>=` усі тести проходять.
Змінено лише `baseScore` у синтетичних даних — це перевірка логіки
порівняння, а не перерахунок CVSS.

## 5. Висновки

Локальні тести перевіряють логіку програми повністю відтворювано: вибір
оцінки, правило варіанта на межі порога, обробку відсутніх і некоректних
даних, коди завершення CLI, а також те, з якими параметрами клієнт
викликає Requests і як реагує на мережеві та HTTP-помилки. Мережа в
тестах заблокована автоматичною фікстурою.

Перевірки з реальним сервісом потребують: фактична доступність NVD, TLS,
обмеження частоти запитів (403/429), дійсність ключа та відповідність
справжньої відповіді очікуваній структурі. Дані NVD змінюються, тому
живий результат не закріплюється в автоматичних тестах.

Брак даних (`insufficient_data`) або `other` не означає відсутності
небезпеки: оцінку можуть ще не призначити, вона може бути лише в іншій
версії CVSS, а базова оцінка не враховує контекст конкретної
організації. Такі записи потребують окремого аналізу, а не автоматичного
віднесення до безпечних.
